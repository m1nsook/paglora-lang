# Paglora Languages

**Translation core for [Paglora](https://github.com/m1nsook/paglora).** Help make Paglora Studio and generated documentation websites usable in more languages.

**Status:** Translation infrastructure **v1**. English is the canonical fallback. Polish and Korean catalogs are the first maintained starting points; **these do not imply that every part of Studio or every Markdown page is translated yet**.

## What is translated?

| Domain | Examples | Where it appears |
| --- | --- | --- |
| `studio.*` | Workspace, project manager, settings, actions | Paglora Desktop |
| `site.*` | Navigation, theme switcher, code-copy controls | Static websites generated by Paglora |
| `docs.*` | Built-in callout headings | Generated documentation components |

**Not automatically translated:** Your actual Markdown writing (`docs/*.md`), custom links, page titles, user-created navigation groups, or custom CSS. Authors write those in their own language. Studio's interface language and a website's HTML content language are independent settings.

## Contribute a translation

1. [Check existing languages](locales/) or [open a language request](https://github.com/m1nsook/paglora-lang/issues/new/choose) to coordinate. You don't need approval before contributing.
2. **Fork** this repository using GitHub's Fork button, then make your changes in your fork using GitHub Desktop or the GitHub web editor.
3. Copy `locales/en.json` to a valid BCP-47 filename such as `locales/fr.json` or `locales/pt-BR.json`. Keep `schemaVersion`, every message key, and placeholders like `{date}`. Translate **values**, not keys.
4. Set `locale`, `nativeName`, `englishName`, and `direction` (`ltr` or `rtl`). You may translate only the keys you can review: missing keys fall back to English. **Remove untranslated English entries** from partial locale files instead of leaving them as fake translations.
5. Run `node scripts/validate.mjs` and `node --test` with Node.js 20+ (or let CI validate your PR).
6. Open a **pull request from your fork to this repository's `main`**. Describe the language, native-language review, and what remains untranslated. CI checks every PR. Maintainers review and merge.

**Use pull requests for submissions—not issue comments linking forks.** Issues are for language requests, terminology questions, coordination, and bug reports. If GitHub blocks your PR, link your fork in an issue only as a fallback.

## Catalog rules

- `locales/en.json` defines the keys and canonical English strings.
- Other locale files contain a **subset** of those keys. Any unknown or missing key is rejected (unknown) or falls back to English (missing).
- ICU-style complexity is **not** part of v1. Simple named placeholders `{name}` must match English exactly. Never translate placeholders.
- Escape rules: values are plain UTF-8 text, **not HTML**, Markdown or JavaScript. Do not insert tags, scripts, control characters or line breaks.
- Keep UI messages concise, understandable and accessible. Preserve technical terms when appropriate; feel free to include an explanation in the PR.
- RTL locale support is recorded in metadata and will be rolled out through each UI surface; setting direction does not automatically translate author-written Markdown.

## Translation lifecycle

The source of truth is this repository. Paglora Desktop bundles **reviewed snapshots** of these locale files for offline use; it must never fetch third-party translation code at runtime. The main project's versioned synchronization process must validate catalogs before updates.

Changes to existing keys require coordination with Paglora to avoid breaking released translations. Do not rename message IDs casually. New UI strings should be added to English first, then translated incrementally. The [contribution guide](CONTRIBUTING.md) explains review expectations.
